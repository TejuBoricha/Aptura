# Aptura's repository presentation

The README introduces a **personal library, precise playback and offline ownership**, then gives developers a direct source-build path. The approved Fold mark and “Every frame. All yours.” campaign provide continuity with the Play listing. The repository compositions are designed for GitHub, rather than displaying the portrait store posters as a gallery.

## What changed and why

The previous README put phone, tablet, landscape and very tall sheet captures in the same Markdown table rows. At its specified widths, a phone library was about 542 px tall, a player sheet about 1,034 px, a landscape player about 166 px and a tablet about 225 px. Their proportions were technically preserved, but their scale and empty space were not composed. The live mobile view compressed three columns until controls were too small to inspect.

The replacement uses three visual chapters: a player-led hero, the adaptive library, and large native control details. Each has a separate narrow-screen composition selected through `<picture>` at 850 px viewport width. The mobile versions remove competing views and enlarge meaningful controls. Fine file metadata can be inspected through linked native crops.

The README keeps the important information as real Markdown text. Image labels and decorative numbering are supplementary; product claims, features, installation, readiness, privacy and contribution routes remain accessible without the images.

## Assets and sources

| Asset | Desktop | Narrow |
|---|---|---|
| Hero | 1600 × 900 | 900 × 1120 |
| Library | 1600 × 930 | 900 × 1380 |
| Controls | 1600 × 1200 | 900 × 1630 |

All six are WebP images under `docs/assets/showcase/`. Native UI crops are linked from [the feature guide](FEATURES.md#ui-gallery). The 1280 × 640 `social-preview.png` is a separate share-card asset; it has not been applied to the repository's social-preview setting. The approved app icon, logo and Play Store artwork are unchanged.

The compositor extracts embedded native PNG captures from the self-contained SVGs in `distribution/play-store/editable/`. It selects them by exact native dimensions and fails on missing or ambiguous matches. The controls and screen content are not generated by an image model. Library and control views are Compose renders with demo data; the player is an Android emulator capture of the real app. Crops retain source proportions, with no screenshot skew or UI repainting.

The mountain, street and other demo scenes are original generated sample media from the listing work. They represent local personal files, not an included streaming catalogue. Continue watching and Library correctly show the same title and thumbnail for the same file. These renders do not verify physical audio quality, HDR, Bluetooth or accessibility.

The optical-glass artwork was created with the built-in image-generation tool for this presentation. It is used only in the share card; the README hero is deliberately quieter. Its selected, optimised source and exact prompt are in `assets/showcase/source/`. No font files are distributed. The compositor uses Arial and Georgia, and the checked-in raster exports fix their appearance.

## Rebuild the visual system

The source is [`tools/presentation/render-showcase.mjs`](../tools/presentation/render-showcase.mjs). It resolves paths from the script location and requires Node.js and Sharp. Sharp is a presentation-authoring dependency, not an app dependency.

To install authoring tools in ignored build output:

```bash
npm install --prefix build/presentation-tools sharp
```

Then set `APTURA_SHARP_MODULE` to the absolute path of `build/presentation-tools/node_modules/sharp` and run:

```bash
node tools/presentation/render-showcase.mjs
python3 tools/presentation/check_showcase.py
python3 -m unittest discover -s tools/presentation
```

For example, in PowerShell:

```powershell
$env:APTURA_SHARP_MODULE = Join-Path (Get-Location) 'build/presentation-tools/node_modules/sharp'
node tools/presentation/render-showcase.mjs
py -3 tools/presentation/check_showcase.py
py -3 -m unittest discover -s tools/presentation
Remove-Item Env:APTURA_SHARP_MODULE
```

Use Arial and Georgia when regenerating for consistent typography. Other machines may substitute different fonts. The renderer exports the authored SVGs and the alternate hero study under ignored `build/review/repository-showcase/`, and writes the fixed WebP/PNG assets and manifest into the repository. Check the rendered images after every regeneration; metadata cannot judge design quality.

## Checks that keep it maintainable

`manifest.json` records source hashes, output hashes, actual dimensions, file sizes and native UI placements. Source text hashes normalise line endings, so Windows and Linux agree. If a canonical capture or the compositor changes, regenerate the images and inspect the result rather than updating hashes by hand.

The dependency-free Python check verifies:

- Local Markdown/HTML image paths and links, including Markdown heading anchors.
- Meaningful alternative text and the three responsive picture groups.
- Source drift, output hashes and PNG/WebP header dimensions.
- Preserved UI aspect ratios and frames contained within their canvases.
- A 1.2 MB total budget for all six primary responsive images. A browser selects three for its viewport; linked native crops are separate.
- No script, iframe, inline event handlers or custom styles in the authored Markdown.

Failure-path tests cover missing links/anchors, escaped paths, empty manifests, changed inputs, corrupt/truncated images, image budget violations, distorted/clipped UI and inaccessible/active markup. The local gate and CI run these checks through the test suite.

Do not use moving test counts, dependency-version badges or an unqualified “all green” statement as evergreen product claims. CI is linked live. JDK, SDK, APK output names and release availability should be rechecked when build/distribution changes. The architecture document points to `APTURA_DB_VERSION` as its schema authority.

## GitHub compatibility and review

The layout uses native Markdown, `<picture>`, `<source>`, `<img>`, `<details>` and `<summary>`. It contains no custom CSS, scripts, remote animation service or external font dependency. The only remote image in the README is GitHub's own CI badge. The [official GitHub writing guide](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/quickstart-for-writing-on-github) documents picture-based responsive images. GitHub's Markdown API preserved this project's viewport-based source attributes during validation.

Two hero approaches were compared: the quiet, light player-led composition and a dark instrument view with a dense precision panel. The first makes the core product easier to recognise. A read-only second review then led to removing the duplicate phone from the hero, separating phone/tablet frames so the adaptive sidebar remains visible, moving a caption away from UI metadata, expanding the mobile library's bottom margin, and increasing the mobile feature headings. The control chapter was also reworked from three narrow columns into wider native details.

The live repository and branch README are checked at desktop and mobile widths. Record the actual inspected viewports, results and any remaining limitations in the PR's Verification block. A local approximation or Markdown API response alone is not a claim of live GitHub visual verification.

## Reference study

The [LocalSend README](https://github.com/localsend/localsend) was inspected for its clear product framing and explicit installation paths. Aptura has a narrower platform and a pre-release distribution state, so its README uses a single build entry rather than a large platform/download matrix. Its visual identity and compositions were developed from Aptura's own mark and UI.

The WebP header checks follow the [Google container specification](https://developers.google.com/speed/webp/docs/riff_container) and [lossless bitstream header](https://developers.google.com/speed/webp/docs/webp_lossless_bitstream_specification). They inspect headers and integrity metadata, not a full pixel decode or subjective readability.
